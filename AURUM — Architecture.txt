AURUM — Architecture, Datasets & Tech Stack for a Minimal MVP
For AURUM, I recommend building a customer-facing gold verification and exchange transparency platform rather than attempting to build a complete jewellery testing system from scratch.

The MVP should demonstrate one complete transaction:
1. A customer enters or scans their jewellery details.
2. The jeweller records physical verification results (purity, weight and deductions).
3. AURUM retrieves the applicable gold price.
4. The system calculates the estimated fair exchange value.
5. Both parties receive an evidence-backed transaction report.
6. AI flags missing, inconsistent or suspicious records.
The most important design decision is to keep physical gold verification, financial calculations and AI-assisted record analysis as separate modules. AI should not invent purity measurements or determine the actual gold content from an ordinary photograph.

Rather than training a new model, create a small labelled dataset of transaction inconsistencies.

My recommendation: use a rule-based anomaly engine first, and use an LLM to explain its findings in understandable language. You can add trained anomaly-detection models when you have enough real, consented and labelled transaction data.

5. Core calculation engine — AURUM's most important feature
This is the part that should be completely deterministic, transparent and testable.
Example gold exchange calculation
Suppose a customer brings a 22K gold chain.
Sample transaction
Gross weight
12.50 g

Stone weight
0.50 g

Net gold weight
12.00 g

Purity
91.6%



Calculation

Illustrative reference rate: ₹12,000/g for 999 gold. This is a hypothetical input, not a current market quote.
\[
\text{Pure gold equivalent}
=12\times0.916=10.992g
\]

\[
\text{Gold value}=10.992\times ₹12,000
\]

₹1,31,904
Illustrative gross metal value before any applicable refining, melting or other agreed deductions.

Calculation logic
\[
V = W_n \times R_{999}\times\frac{P}{999}
\]

Where:
- \(W_n\) = net gold weight in grams.
- \(R_{999}\) = reference price per gram of 999 gold.
- \(P\) = measured fineness, such as 916.
If using the IBJA 916 rate directly, calculate using that rate per gram and do not apply the purity conversion again.

Then:
\[
V_{\text{offer}}=V-D
\]

Where \(D\) represents individually itemised, agreed deductions.

For example:
- Melting/refining deduction.
- Other documented adjustments.
- Applicable transaction-specific charges.
Do not hardcode a universal deduction percentage. Store the reason, amount, calculation method and party accepting it.
What makes this feature valuable?
Instead of displaying only a final price, AURUM should show:
1. Gross jewellery weight.
2. Deducted non-gold weight.
3. Measured purity.
4. Reference gold rate and timestamp.
5. Calculated metal value.
6. Each deduction separately.
7. Final jeweller offer.
This makes the financial calculation explainable and allows customers to compare the jeweller's offer against the documented calculation.

6. Database architecture
Use PostgreSQL through Supabase.

I recommend these seven initial tables:
Table	Important fields	Purpose
users	id, name, role, phone	Customer/jeweller accounts
jewellery	id, owner_id, type, gross_weight, purity	Jewellery information
verifications	jewellery_id, HUID, XRF result, verified_by	Physical and hallmark evidence
gold_rates	date, purity, rate, source, session	Historical reference prices
transactions	id, customer_id, jeweller_id, jewellery_id, final_offer	Exchange records
evidence	transaction_id, file_url, evidence_type, timestamp	Photos and documents
anomaly_flags	transaction_id, flag_type, severity, explanation	AI/rule-based warnings

Important database feature: Transaction history
Every transaction should preserve a snapshot of the values used at that time.

For example, if the gold rate changes tomorrow, yesterday's transaction must not change.

Store:
- Rate value.
- Rate source.
- Rate date and session.
- Purity used.
- Weight used.
- Deduction breakdown.
- Calculation version.
- Evidence references.
- Customer and jeweller acceptance timestamps.
For privacy, configure Supabase Row Level Security so customers can access their own transactions and jewellers can access only transactions they are authorised to handle. Keep privileged API keys on the server.

7. AI implementation: What should AI actually do?
I would avoid claiming that AURUM uses AI to determine the actual purity of gold. That would require validated physical measurements and a suitable scientific model.

Instead, give AI three useful responsibilities.










AI Feature 1 — Evidence extraction

Extract relevant details from uploaded receipts, reports and transaction documents.

Example: Extract weight, purity, jeweller name and transaction date from a bill.
MVP feasible













AI Feature 2 — Inconsistency detection

Compare declared purity, recorded purity, HUID information and weight.

Example: Declared 22K, but recorded XRF result is 18K. Flag for review.
MVP feasible













AI Feature 3 — Explainable transaction reports

Convert technical measurements and calculations into understandable customer-facing explanations.

Example: Explain why the offer differs from the reference gold value.
MVP feasible



Suggested AI workflow
Transaction records + uploaded evidence

Structured data extraction (Gemini)

Deterministic validation engine

AI explanation of detected inconsistencies

AURUM evidence and risk report


The deterministic validation engine should decide whether a discrepancy exists. The LLM should explain the discrepancy, not decide whether a transaction is fraudulent.

13. Final recommendation: What to prioritise
Not every proposed feature contributes equally to AURUM's novelty.
Feature	MVP importance	Novelty potential
Gold exchange calculator	Very high	Medium
HUID verification workflow	Very high	Medium
Evidence-backed transaction records	Very high	High
Customer–jeweller shared history	High	High
AI inconsistency detection	High	High
Automated XRF integration	Low initially	High
Blockchain transaction records	Not necessary	Low without a specific use case
AI gold purity prediction from images	Avoid initially	Unproven

My recommended MVP combination
Build these five features exceptionally well:
1. Jewellery registration and physical verification records.
2. BIS HUID verification with supporting evidence.
3. Transparent gold exchange valuation.
4. AI-assisted inconsistency detection.
5. Shared, timestamped customer–jeweller transaction reports.
This is a much stronger prototype than a simple gold price calculator with an AI chatbot.

One particularly important differentiator: preserve the complete evidence and calculation state of every transaction so that either party can later reconstruct exactly how an exchange offer was calculated and which information supported it. This is the foundation of AURUM's proposed dispute-replay capability.

My suggestion is to build the first version as a web application, make the transaction calculation engine the technical core, and treat AI as an additional intelligence layer rather than the foundation of the application.
